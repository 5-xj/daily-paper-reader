## 摘要
常数优化在符号回归的树型遗传编程中微调候选表达式的数值系数。但其每代的计算成本导致现代GPU加速框架要么省略该步骤，要么将其限制为轻量级形式。我们提出了一种GPU驻留的批处理Levenberg--Marquardt求解器，在结构异质的表达式树种群中优化常数，每次迭代仅使用固定数量的全种群CUDA启动。逆向模式自动微分在单次反向扫描中组装每棵树的雅可比矩阵，使得每次迭代的主导成本与每棵树的常数数量无关，而双精度交付保证确保返回的常数永远不会比其初始值更差。在早期种群中，该求解器在NVIDIA A100上可持续处理高达每秒$5.1\times10^{5}$棵树；在GPU饱和的基准配置下，其吞吐量约为64核EPYC 7763上Operon的$9.9\times$，同时匹配fp64参考质量。该求解器集成在EvoGP进程中，使端到端搜索能够在18个构造问题中的10个上恢复控制方程，而原版EvoGP则为0。我们的代码位于https://github.com/TensorConv/CuSR。

## Abstract
Constant optimization refines the numerical coefficients of candidate expressions in tree-based genetic programming for symbolic regression. But its per-generation cost has led modern GPU-accelerated frameworks to omit it or restrict it to lightweight forms. We present a GPU-resident, batched Levenberg--Marquardt solver that optimizes constants across a structurally heterogeneous population of expression trees using a fixed number of population-wide CUDA launches per iteration. Reverse-mode automatic differentiation assembles the per-tree Jacobian in one backward sweep, making the dominant per-iteration cost independent of the number of constants per tree, and a double-precision delivery guard guarantees that returned constants are never worse than their initial values. On early-generation populations, the solver sustains up to $5.1{\times}10^{5}$ trees per second on an NVIDIA A100; at a GPU-saturated benchmark configuration it delivers roughly $9.9{\times}$ the throughput of Operon running on a 64-core EPYC 7763, while matching fp64-reference quality. Integrated in-process into EvoGP, the solver enables end-to-end search to recover governing equations on $10$ of $18$ constructed problems versus 0 for stock EvoGP. Our code is at https://github.com/TensorConv/CuSR.

## 1. 核心问题与整体含义

- **背景**：符号回归（Symbolic Regression, SR）旨在从数据中发现闭式数学表达式，核心是在模型结构与数值系数上进行联合搜索。树型遗传编程（Tree-based Genetic Programming, TGP）是主流方法，通过选择、子树交叉、变异等算子进化表达式树。
- **痛点**：遗传算子擅长改变树结构，却不擅长微调实值常数。一个结构完全正确的表达式可能因系数不精准而获得很差的适应度，从而在进化中被淘汰。常数优化（Constant Optimization, CO）每代都对候选表达式进行数值拟合，但计算代价高昂。
- **现代框架的困境**：因为 CO 成本过高，许多 GPU 加速符号回归框架干脆省略该步骤，或用轻量级手段（如受限迭代的 BFGS）替代：
  - PySR：仅限 CPU，受限迭代预算；
  - Operon：CPU 绑定，吞吐受限；
  - EvoGP：GPU 高吞吐且支持种群级并行，但**原生不支持常数优化**，导致其搜索精度受限——特别是对“内部常数”（如 sin 内的频率、exp 内的衰减率）无法有效拟合。
- **核心研究问题**：能否让常数优化在 GPU 上以**批处理方式**高效执行，使其可以在每一个进化世代中运行，且不影响 GPU 符号回归的吞吐优势？
- **方法路线**：作者提出了一个 GPU 驻留的 **批处理 Levenberg–Marquardt（LM）求解器**，能在一个结构异质（各树常数个数不同）的表达式树种群上统一优化常数，且每次迭代只启动固定次数的全种群 CUDA kernel。最后将该求解器**集成到 EvoGP** 中，实现了端到端的闭环。

## 2. 方法论

### 2.1 核心思想

- 以“种群”而非“单棵树”为单位进行常数优化。
- 所有树的常数放在一个连续扁平向量中，通过 per-tree 的 offset 来索引；结构数组只上传一次、不会在迭代中重写。
- 将一个 CUDA warp 分配给一棵树，warp 的 32 条 lane 拆分数据行；每棵树的 Cholesky 求解用单线程完成。
- 每次 LM 迭代只启动**固定次数（8 次）的全种群 kernel launch**，与树的数量及各自的常数个数无关。
- 引入**双精度交付保证**：高斯-牛顿内环在 fp32（fast-math 编译）下运行，但最终交付前在 fp64 下重评估，保证返回的常数不会比初始值差。

### 2.2 批处理 LM 工作流

论文给出的优化流程（Algorithm 1）可以概括为：

1. **初始化**：常数初始化为传入值，阻尼参数 λ 初始设为统一值，每棵无常数树直接跳过。
2. **初始损失评估**：第一次批量评估计算每棵树在初始常数下的损失 ℓ*（残差向量 r 被填充）。
3. **循环迭代（外层循环在 host，内部八次批量启动）**：
   - 若有任何树处于 active 状态，则进入迭代；
   - **构建雅可比**：对所有 active 树、每个数据行，用反向模式自动微分获得雅可比矩阵行；
   - **组装法方程**：形成 A = J^T J 和 g = J^T r；
   - **求解** damped normal equation：(A + λ diag(A)) δ = -g，通过 Cholesky 分解（非正定则失败）；
   - **试步损失评估**：在 c+δ 上用 fp32 批量重评估损失；
   - 逐树接受/拒绝试步（该步在 host 侧仅交换不涉及 N 的每树小状态）。
4. **终止条件**：所有树收敛、失败或达到最大迭代次数 t_max。
5. **fp64 交付保证**：对所有树在 fp64 下用初始与最终两组常数重新计算损失，若最终损失非有限或更差则回退到初始值。

### 2.3 雅可比构建：三种模式

| 模式 | 行构建方式 | 每行 walk 次数 | 构建成本 | 每行额外寄存/存储 |
|---|---|---|---|---|
| 有限差分 | 逐个扰动常数 | K_m | O(K_m * N * n_m) | 128 B |
| 前向 AD | 每次携带 8 个切向量 | ceil(K_m/8) | O(ceil(K_m/8) * N * n_m) | 2.0 KB |
| 反向 AD | 一次录带前向 + 一次反向扫 | 2 | **O(N * n_m)**（与 K_m 无关） | 1.25 KB |

- 关键性质：**反向 AD 的雅可比构建成本与树中常数个数 K_m 完全无关**。
- 反向传播乘法的具体技巧：当某一因子恰好为 1 时乘积视为 0，防止 0×∞ 出现 NaN 并污染整个列。
- 每棵树最多允许 32 个常数，64 层深操作数栈，128 节点磁带，这些是编译期限制，可调整。

### 2.4 fp64 交付保证

- 快路径 fp32 + fast-math 用于提升吞吐。
- fp64 检查只发生在**交付边界**（循环结束后一次），而非每一次迭代，因此开销很小（每棵树两次额外 fp64 评估）。
- 理论上保证：交付常数在双精度下不劣于初值。

### 2.5 与 EvoGP 的集成

- 求解器以**进程内**方式加载进 EvoGP。
- 每一代进化中，种群所有树的常数传给求解器作一次批量拟合，然后写回。
- 拟合失败的树保留继承的初始常数。
- 关键消融发现：**每 5 代调用一次 CO** 与每代调用在恢复方程数量上统计无显著差异，可大幅节省成本。

## 6. 主要结论与发现

1. **吞吐**：批处理 CUDA LM 求解器在 A100 上（早期世代工作负载，M = 256,000 棵树，N = 100 点/树）达到最高 **约 5.1×10⁵ 树/秒**。吞吐随种群规模增大而持续上升（10³ 的 39,717 树/s 提升到 2.56×10⁵ 的 511,308 树/s，约 12.9 倍），体现出批次化分摊启动开销的优势。
2. **与 CPU 的对比**：在 GPU 饱和配置（M = 16,000，N = 1,000）下，吞吐为 **98,154 树/s**，对比 Operon（9,959 树/s）是 **约 9.9×**，对比 SciPy 参考（5,310 树/s）是 **约 18×**。
3. **数据点影响**：随 N 增长（100→10,000），对 Operon 的优势收窄为 2.7×，但点处理吞吐仍持续上升（2.6×10⁷→1.2×10⁸ 点/s），说明是 CPU 侧也在更好地摊销固定开销，而非 GPU 效率下降。
4. **算法模式**：反向模式 AD 为默认。前向 AD 在常数少时小幅领先（0.95×），常数多时 rev AD 优势明显（最大 1.43×），整体中位数优势为 fwd AD 的 1.11×、FD 的 1.51×。
5. **瓶颈定位**：循环既非算力饱和也非带宽饱和（FMA 利用率 ≤15%，DRAM 利用率低于 23%），主要受指令发射与片上延迟限制。意思就是说瓶颈不在“算”，而在于一棵树的依赖链过长、不规则判断多、指令发射吞吐不足；批量处理提供足够的并行树来遮掩这种延迟。
6. **质量与高速**：能与 fp64 参考质量匹配。86.6%–93.8% 收敛树损失落在参考的 1.05× 以内；不同 GPU 模式间 Spearman 相关高达 0.959（rev AD vs FD）及 0.995（两 AD 模式之间）。进化选择主要依赖排序，微小差异不改变选择结果。
7. **常数优化的必要性**：在 18 个构造问题中，原版 EvoGP 恢复 0 个；集成批处理 LM 后恢复 **10/18** 个真实方程。每五代优化与每代优化效果高度相似（p = 0.73）。
8. **填充代价**：采用固定形状布局将性能降低 4.45 倍（数据相同、结果相同，差异纯由内存布局所致），验证了紧凑非填充布局设计的价值。

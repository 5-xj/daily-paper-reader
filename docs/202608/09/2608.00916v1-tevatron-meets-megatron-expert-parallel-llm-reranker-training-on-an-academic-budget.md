## 摘要
现代重排序方案——十亿级交叉编码器、混合专家（MoE）主干网络以及针对强教师的蒸馏——已经超出了大多数学术团队可用的训练基础设施。现有的 Tevatron 重排序器训练依赖基于 Hugging Face Trainer 的 DeepSpeed 或 PyTorch FSDP1，但这些后端缺乏对大规模 MoE 训练的高效支持。我们提出了 Tevatron 3.0，它将 Megatron-Core 训练后端集成到 Tevatron 中，同时保留其数据管线、评估工作流和与 Hugging Face 兼容的检查点。我们将现有的分布式训练配置与新后端进行了基准测试，结果表明，在可比较的数据并行设置下，Megatron 与 FSDP 重排序器的质量和训练效率相当；在推荐的单节点配置中，速度最多可提升 22%，并同时支持 LoRA 和全参数微调。关键在于，专家并行使得训练 300 亿参数的 Qwen3-30B-A3B MoE 重排序器成为可能，而这在 PyTorch FSDP1 下是不可行的。利用这一框架，我们进行了受控对比实验，比较了 MoE 与稠密模型、LoRA 与全参数微调、以及蒸馏与对比训练在 BEIR-15 上搭配三个第一阶段检索器的效果，并报告了 Hugging Face 和 vLLM 的服务吞吐量。我们发现，MoE 重排序器在激活不到一半参数的情况下达到了稠密 8B 模型的质量，并实现了显著更高的推理吞吐量。我们将发布该框架和训练好的检查点。

## Abstract
Modern reranking recipes---billion-scale cross-encoders, mixture-of-experts (MoE) backbones, and distillation against strong teachers---have outpaced the training infrastructure available to most academic groups. Existing Tevatron reranker training relies on the Hugging Face Trainer with DeepSpeed or PyTorch FSDP1, but these backends lack efficient support for large-scale MoE training. We present Tevatron 3.0, which integrates a Megatron-Core training backend into Tevatron while preserving its data pipeline, evaluation workflow, and Hugging Face-compatible checkpoints. We benchmark existing distributed training configurations against the new backend, showing that Megatron matches FSDP reranker quality and training efficiency under comparable data-parallel settings, is up to 22% faster in the recommended single-node configuration, and supports both LoRA and full-parameter fine-tuning. Crucially, expert parallelism enables training a 30B-parameter Qwen3-30B-A3B MoE reranker, which is infeasible with PyTorch FSDP1. Using this framework, we conduct a controlled comparison of MoE versus dense models, LoRA versus full-parameter tuning, and distillation versus contrastive training on BEIR-15 with three first-stage retrievers, and report serving throughput for Hugging Face and vLLM. We find that the MoE reranker matches dense 8B quality while activating less than half as many parameters and achieving substantially higher inference throughput. We will release the framework and trained checkpoints.

  - **DeepSpeed ZeRO-2 不可靠**：存在已知的 CPU 卸载梯度累积 bug，导致 ZeRO-2 分片在实际中失败。
  - **PyTorch FSDP1 全分片吞吐效率低**：对于 8B 重排序器，ZeRO-2 和 ZeRO-3 两者所需时间几乎相同，更重的分片并未带来速度提升，且都慢于分布式优化器后端。
  - **缺乏专家并行（Expert Parallelism, EP）**：PyTorch FSDP1 不支持 EP，导致 MoE 重排序器（如 Qwen3-30B-A3B，128 个专家）无法被高效训练——只能复制再分片专家，而无法路由激活子集。
- **核心问题**：如何在学术预算（有限的 GPU 资源和单一作业）下高效训练并部署大规模（尤其是 MoE）LLM 重排序器？

## 2. 方法论：核心思想与技术细节

### 2.1 总体设计理念

- **可替换性（Substitutability）**：用户仅需更改启动脚本即可切换训练后端，无需修改数据、评估流程或检查点格式。新后端复用现有数据路径、collator 和 BEIR 评估模块。
- **双向权重桥（Weight Bridge）**：预训练 HF 检查点在加载时被分片为 Megatron 并行布局，训练后的模型在保存时导出回 HF 格式。全参数微调和 LoRA 分别使用对应的桥接保存路径（后者写入预合并权重），保证所有检查点可直接通过标准 HF 和 vLLM 路径加载。

### 2.2 重排序器评分与训练目标

- **评分方式**：将查询-文档对格式化为模板 `query_prefix + query + passage_prefix + passage + "relevant:"`，使用生成式重排序器计算最终位置 "yes"/"no" 答案标记的 log 概率之差作为标量相关性得分：\(s_\theta(q,p) = z_\theta(q,p)_{yes} - z_\theta(q,p)_{no}\)。
- **分组**：每个 query 的 1 个正样本和 G-1 个难负样本被独立评分并重塑为分组得分向量 \(s_i \in \mathbb{R}^G\)。
- **两种损失函数**：
  - **对比学习（Contrastive）**：正样本固定位于每组索引 0 处，使用列表式交叉熵损失 `F.cross_entropy(grouped_scores, labels)`。
  - **蒸馏学习（Distillation）**：学生分布（softmax 学生得分/学生温度）与教师分布（softmax 离线教师得分/教师温度）之间使用列表式 KL 散度，乘以学生温度平方。教师得分离线预计算并存储于训练数据中，训练时不需要额外的教师模型或前向传播。

### 2.3 并行策略

- **并行拓扑**：由三个标志配置——张量并行（TP）、管道并行（PP）和专家并行（EP）；数据并行推导为 DP = world_size / (TP · PP)，EP 与 DP 正交。
- **分布式优化器**：采用 Megatron 的分布式优化器（ZeRO-1 风格：优化器状态在 DP  ranks 间分片，参数和梯度复制）。
- **TP 作为参数/梯度分片的近似**：当前通过张量并行实现参数/梯度分片；直接的 FSDP 风格 ZeRO-2/3 数据并行分片留待未来工作。

### 2.4 LoRA 目标组注册表

- 针对 MoE 模型的 LoRA 应用存在陷阱：稠密 MLP 模式可能静默匹配所有 128 个专家 FFN。
- 提供命名目标组注册表，映射角色到模块模式：
  - `attn`: attention 模块
  - `mlp`: 仅稠密 MLP
  - `moe_experts`: 所有专家 FFN（`*.experts.*.linear_fc1/fc2`）
  - `moe_shared`: 共享专家
  - `moe_router`: 路由器（通常冻结）
- 实验中采用 `attn + moe_experts + moe_shared` 规范，冻结路由器以保持稳定性。

### 2.5 评估与服务管线

- 将评估分解为三部分：不变的度量核心（NDCG@k / Recall@k / MAP / MRR）、基准注册表（数据集、qrels 来源、聚合方式）和表格渲染器。
- 支持两种使用模式：
  1. **仅评分（本地）**：给定现有 ranklists，直接评分聚合，无需加载模型。
  2. **远程后端池重排序+评分（HTTP）**：重排序器作为持久评分服务器（vLLM 或 HF 后端），通过 HTTP API（`POST /score`）提供统一契约；评估器作为瘦客户端，可对多个后端 URL 进行负载均衡。

## 6. 主要结论与发现

- **MoE 匹配稠密质量且更高效**：30B-A3B MoE 重排序器在所有三个第一阶段检索器和四种训练配置下，均与稠密 8B 质量在 0.006 NDCG@10 内一致，但激活参数不到一半（~3B vs ~8B）。
- **推理吞吐量优势显著**：MoE 在 HF 后端比稠密 8B 快 1.15×，在 vLLM 后端快 1.43×；vLLM 比 HF 整体快 3.2-3.9×；最佳组合（vLLM × MoE）达到 2,622 pairs/s，是最差组合（HF × 8B）的 4.5 倍。
- **LoRA 恢复大部分全参数质量**：稠密 8B 上 LoRA 仅落后全参数 ~0.007-0.011 NDCG@10；MoE 上专家感知的目标规范是实现这一恢复的前提。
- **蒸馏是配方依赖的正则化器**：蒸馏在噪声/分级相关性任务上有帮助，但在单一明确答案的任务上有害；同规模教师（8B）缺乏容量余量，且难负样本已被去噪，限制了蒸馏的潜在价值。
- **后端效率结论诚实**：匹配拓扑下 Megatron 仅比 FSDP1 快约 4%，显存约为 2×；22% 的头号差距主要来自 Megatron 能在内存预算内运行更轻通信的拓扑，而非框架内在速度优势。

## 7. 优点

- **系统的向后兼容性**：数据路径、评估流程和 HF 检查点格式完全不变，用户仅需更改启动脚本即可迁移。
- **针对 MoE 的明确解决方案**：专家并行将每 rank 专家内存降低到 experts/EP，使 30B MoE 训练在双节点 8×H200 上可行（峰值 78.9 GiB/GPU）。
- **MoE-aware LoRA 注册表**：解决了稠密模式误匹配专家 FFN 的陷阱，使低秩适配能正确作用于专家层。
- **统一的评估/服务接口**：本地评分与远程后端池（HF/vLLM）可互换，吞吐量矩阵是一行后端切换的结果。
- **实验对比的严谨性**：区分"推荐配置"与"匹配拓扑"两个层次，避免误导性的框架内在加速声称；多检索器评估考虑了一阶段质量差异。
- **可扩展性设计**：新损失函数、新架构、新评估基准、新推理后端均只需添加分支/条目/子类，无需改动核心机制。

## 8. 不足与局限

### 实验覆盖方面

- **蒸馏实验不完整**：仅使用同规模 8B 教师、单一温度（教师 2.0 / 学生 1.0）、单一组大小，缺乏对温度、组大小和教师容量（尤其更大教师）的系统扫描，无法得出蒸馏价值的普遍结论。
- **缺乏更广泛模型家族与规模的验证**：仅测试了 Qwen3 系列的两个模型；更小/更大的模型、不同的 MoE 结构的泛化性未知。
- **训练数据单一**：仅在 RLHN-680K 上训练，未测试其他训练数据配方的兼容性。

### 偏差风险

- **健全性检查非严格受控**：与 RankT5/RankLlama/RankQwen 的对比中，基线使用不同的训练数据、第一阶段和设置，不能直接解读为论文模型的竞争性优势。
- **作者承认**：论文中的 checkpoint 是固定配方下的产物，未针对榜单成绩进行调优；宏观平均可能掩盖每任务层面的结构性差异。

### 应用限制方面

- **MoE 训练成本仍然较高**：需双节点 2×8×H200（EP=16, DP=16），虽在学术预算内但门槛仍不低。
- **ZeRO-1 显存代价**：匹配 FSDP1
